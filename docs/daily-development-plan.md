# Private Talk 每日开发与双站发布方案

制定日期：2026-10-27。用户已授权按本方案持续改进、验收后部署 Cloudflare 与 VPS，并更新 GitHub。

## 产品目标与约束

- 公开桌游优先：无需注册，从首页快速找到能玩的桌，完成一局。
- 私密聊天同样必须安全、实时；既有端到端加密、签名、严格模式与前向保密不得因游戏功能降级。
- 不收集用户个人数据，不建立账号、画像、长期用户标识或行为分析；不接入广告追踪或第三方统计。
- 只临时处理连接、限流、座位和对局必需的数据。逐项列明生命周期；实际托管平台日志设置也必须核对。不能承诺网络基础设施完全看不到 IP。
- 公开桌游中服务端裁判可知的信息与端到端加密聊天必须分别说明。
- 不伪造在线人数、玩家、对局、测试结果或发布成功；不为赶每日进度绕过验收。
- 默认沿用现有技术和玩法，不新增大型依赖，不自行重写密码协议。

## 执行方式

采用每天一个可验收改进的小步发布。集中做大版本会延迟反馈；只巡检不开发不能实现本次目标，因此不采用。每天纽约时间 09:00 执行，按下面顺序选择第一个未完成任务；任务跨日时继续，不按日历强行跳过。

本文件是长期路线图。每日开始时先检查最新代码；已有能力经过测试证明后可以直接标记完成，避免重复开发。每项开始前在工作记录中补充实际改动文件、具体行为、回归测试和验收标准。

## 首轮任务队列

- [ ] D01 基线与发布能力。运行现有单元、浏览器、Node 与 Cloudflare 测试；核对两站版本与签名、GitHub CI、发布权限、签名密钥可用路径和回退流程。记录真实失败，不把缺少权限误报为测试通过。交付基线报告与阻塞清单。
- [ ] D02 产品与隐私文案一致。以公开桌游为首页主路径，保留清晰的私密入口；对照实现统一 README、说明书与界面。公开桌入口说明裁判可见的数据；修正旧版降级等过期说明。验收：两条入口可用，声明与代码一致，多语言关键提示完整。
- [ ] D03 大厅信息与加入行为。清楚显示玩法、当前人数、开局所需人数、等待/进行中/已满；不显示私密房间。验收：空大厅、过期桌、满桌及并发加入均正确。
- [ ] D04 集中匹配。优先加入适合玩家的待开局桌，避免重复建空桌。验收：并发快速匹配不超员、不错误加入进行中对局、不泄露私密桌。
- [ ] D05 等待与准备。解释还差几人、谁尚未准备、能否开始；避免重复准备/开局请求造成多次初始化。验收：最低/最高人数、成员离开和重复操作均正确。
- [ ] D06 重连。验证短暂断网、网络切换、切后台后返回的座位及游戏恢复；明确服务端或浏览器无法保证的情况。验收：凭证有效/过期、锁房重连、房主掉线和所有人断开不会混淆身份或恢复已销毁的房间。
- [ ] D07 实时状态。区分连接中、已发送、已送达、同步中和发送失败；游戏行动去重并拒绝过期回合。验收：重复、乱序、延迟及断线消息不产生双重行动或虚假送达。
- [ ] D08 对局闭环。优先验证公开狼人杀、密电逃脱和低人数玩法的完整开局、行动、结算与再来一局。验收：隐藏信息仅发给应知成员，结算正确，清理上一局状态。
- [ ] D09 无账号防滥用。检查房间级限速、拖延超时、退出、移出及表决边界；只使用连接/当前对局必要状态。验收：恶意重复操作不能破坏别人正常行动，不引入永久封禁档案或指纹。
- [ ] D10 手机体验。验证窄屏、软键盘、滚动、横竖屏、点击区域与触屏操作。验收：能在手机尺寸完成一局并聊天，不遮挡关键行动。
- [ ] D11 私密聊天安全回归。覆盖成员加入/退出换钥、严格模式、签名校验、安全码变化、图片与送达回执。验收：异常时明确暂停/失败，不静默降级；不在控制台、网址或日志泄漏暗号及明文。
- [ ] D12 数据生命周期审查。核对 Node、Durable Objects、公开裁判状态、附件、定时器、浏览器存储与代理/Cloudflare 配置。验收：必要临时状态按已定义时机删除，不记录个人数据；无法核实的平台留存明确记为待确认。
- [ ] D13 跨后端一致性。Node 与 Cloudflare 执行相同核心场景，检查容量、限速、非法帧、慢连接及清理。验收：不存在某后端独有的越权、泄露或游戏规则差异。
- [ ] D14 全链路验收。复查找桌、加入、开局、完整游戏、聊天、重连、结算及两站发布回退。整理首轮结果和下轮缺陷队列，优先修缺陷；没有证据支持时不增加新玩法。

## 每日执行步骤

1. 获取仓库最新状态，读取本方案及 `docs/daily-progress/` 最新记录。检查 AGENTS.md。保留他人未提交改动；在独立工作区开发，不重置脏工作区。
2. 使用非阻塞的进程锁防止同一项目两个每日任务重叠。已有任务运行就报告跳过，不能同时开发或部署。
3. 选择一个未完成任务，先确认当前实现，写出具体验收。行为修改先补能证明问题的回归测试，再实现，最后检查相关边界和差异。
4. 本地运行相关测试和 `npm test`、`node scripts/build-help.mjs --check`。按照 `.github/workflows/test.yml` 完成浏览器、Node smoke、Cloudflare runtime 验证；通过 GitHub CI 补全三平台与部署包检查。检查必须绑定待发布的准确 commit。
5. 更新工作记录后提交 GitHub，等待该 commit 必需 CI 全部完成。pending、跳过的必需检查、超时、缺少依赖都不是通过。失败则修复或保留分支，不部署。
6. 仅在应用代码或发布资产发生变化时发布；纯计划/工作记录提交不重启网站。发布前记录 commit、版本、签名文件、两站上一个可回退版本和当前活跃对局情况。不能为了看起来每天有发布而重复部署。
7. 按下面双站发布流程执行，分别记录结果。更新完成标记和日报；只在明确达到验收时勾选任务。

## 双站发布与回退

- Cloudflare：`https://chat.freedom8964.com`。使用既有 `scripts/deploy-freedom8964.mjs`；需要有效 Cloudflare 授权及 `RELEASE_SIGNING_KEY`。该脚本要求签名，不允许改成无签名部署。
- VPS：`https://chat.nya.je`。本机已有 `/opt/private-talk` 与 `private-talk.service`，Caddy 代理到本机服务。优先使用现有签名离线包及更新器；确认备份/回退包后更新。不要直接覆盖运行目录。
- 两站部署同一源码 commit、同一版本和已验证的签名资产。签名密钥现有 GitHub Secret 只供 CI 使用；不能把它打印、写入仓库或替换发布公钥。
- 发布权限不足时只完成开发和可复现验收，记录具体缺少的权限/凭证，不宣称已部署。不要把密钥请求写进公开 GitHub 日报。
- Node 重启会断开连接。发布前检查是否有活跃对局；没有可靠检查方法或对局未结束时推迟重启。不能承诺跨站原子发布或无中断更新。
- 一次只发布一站，验证通过再更新另一站。每站验证 HTTPS、首页、大厅 API、签名清单、版本和隔离测试房间的 WebSocket smoke；绝不加入或记录真实用户房间。
- `node scripts/verify-site.mjs <站点>` 和 `node server/smoke.mjs <站点>` 必须返回成功；再核对清单版本/commit 与待发布版本一致，不能只检查 HTTP 200。
- 任一站失败，停止后续发布并按已有机制回退受影响站；核验回退结果。若另一站已经升级，恢复两站至共同已验证版本；不能回退时明确报告版本不一致。
- 一次成功的自动化验收不等于密码学第三方审计或“安全认证”，报告只描述实际完成的验证。

## 日报与后续循环

每次运行创建/更新 `docs/daily-progress/YYYY-MM-DD.md`，包括：任务、具体变更、测试命令与结果、GitHub commit/CI 链接、两站各自发布版本与验证、回退结果、阻塞和下一步。不记录玩家信息、IP、暗号、聊天内容或密钥。当天重跑追加记录，不覆盖历史。

首轮完成后，按“生产故障 → 安全/数据留存 → 无法开局或无法结束 → 重连与实时 → 手机可用性 → 其他体验”的顺序继续。只使用合成测试、代码审查与用户主动反馈，不增加用户追踪。无真实问题时做回归维护，不能为制造进度随意改动。
