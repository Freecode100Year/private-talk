# HTML Room 安全模型

本文说明 HTML Room（`hr1`）保护什么、不保护什么。协议细节见 [protocol.md](protocol.md)，未验证的环境与限制见 [compatibility.md](compatibility.md) 和 [limitations.md](limitations.md)。

## 1. 一句话

**拿到房间文件（或 `#hr1=` 链接）的人就是房间成员。** 房间之内的保护与现有私密房间完全相同（v3.2：前向保密、每条消息一次性密钥、签名、ECDH + ML-KEM-768 混合、离开即换钥）；HTML Room 改变的只是“怎样进入房间”：从“知道暗号”变成“持有文件”。

## 2. 各方能看到什么

| 谁 | 能看到 | 看不到 |
|---|---|---|
| 中继运营方 | 连接者 IP、连接时间、Room ID（64 位 hex）、同一房间有几个连接及其编号、帧的大小档位和时间 | Master Secret、`access` 以外的任何密钥、房间名、消息内容、回执内容、谁是谁 |
| 网络旁观者 | 连接了哪个中继域名（`wss` 加密之后） | 房间、内容 |
| **转发文件的平台**（微信、QQ、邮箱、网盘） | **无口令文件：完整 Master Secret，等同于成员。** 口令文件：加密后的 Master Secret、房间名、中继地址，可离线猜口令 | 口令文件：口令足够强时看不到 Master Secret |
| 网页入口的服务器（仅 `#hr1=` 模式） | 正常请求看不到片段；但它下发页面脚本，**被入侵或作恶时可以下发读取片段的脚本** | 文件模式下不参与 |
| 房间里的其他成员 | 消息、你的编号、你本次访问的签名公钥 | 你的 IP、你是谁 |

中继保存的只有短期的连接路由信息（谁连在哪个房间、编号、断线后 2 分钟内的重连凭据），所有人离开后消失。这依然是元数据，本文不声称中继“不掌握元数据”。

## 3. 文件即钥匙

### 3.1 无口令模式（默认）

配置里直接是 256 位 Master Secret。打开即连，最方便，但：

- 文件经过的每一个系统（聊天软件服务器、邮件服务器、云盘、杀毒扫描、手机备份）都可能留下副本。任何副本都能在任何时候进入房间，并读到**进入之后**的消息。
- 前向保密仍然成立：之前录下的密文，事后拿到文件也解不开（需要当时页面内存中的临时私钥）。
- 页面顶部显示警告：此文件包含完整房间密钥，请勿通过未加密的社交软件直接发送。

### 3.2 口令模式

Master Secret 被打开口令（PBKDF2-SHA-256，60 万轮）加密后写入文件；房间名和中继列表绑定在 AAD 中，被改动后无法解锁。

- 平台拿到文件后**可以离线反复猜口令**，界面上的失败次数限制对它不起作用（因此也没有设置）。强度完全取决于口令：6 位数字约 1 分钟可穷举；生成器“随机生成”的 12 位口令约 60 位强度，见 [protocol.md §3](protocol.md#3-口令模式) 的估算表。
- 口令必须通过与文件**不同的渠道**传达（当面、电话）。口令与文件经同一个软件发送，等于没有口令。
- 口令模式不是“彻底解决”平台截获：它把问题从“平台一定能进”变成“平台需要猜中口令”，前提是口令是随机生成的。

### 3.3 邀请不会过期

V1 没有吊销机制。不再信任某份文件时，创建新房间、发新文件。

## 4. 客户端完整性

### 4.1 文件模式

- 页面的可执行脚本与样式在**所有**房间文件中逐字节相同，其 SHA-256 记录在 [hashes.json](hashes.json)，也写在每个文件自己的 CSP 中。房间之间只有配置块和 `connect-src` 不同。
- 收到文件后可以运行 `node scripts/verify-room-file.mjs 文件.html`：确认脚本、样式、CSP、页面结构与发布的模板一致，并列出它会连接的中继、是否加锁（不显示密钥）。它不能告诉你文件是谁做的，也不能判断中继是否可信——这要看它列出的地址。
- `hr-template.html` 随网站一起列入签名的 `integrity.json`，可以用现有 `scripts/verify-site.mjs` 核对线上模板。

### 4.2 网页模式（`#hr1=`）

- 地址栏片段不随 HTTP 请求发送；页面脚本的第一件事是读取并用 `history.replaceState` 清除它，秘密不写入任何存储，只连接本站 `/hr/`，没有第三方脚本、统计或 Service Worker。
- 但**网页模式依赖网站当时下发的代码**。网站被入侵时，恶意脚本可以读取片段。片段还可能留在：复制出去的链接、浏览器历史（清除前的那一刻）、浏览器扩展、截图。页面上有明确提示，不把网页模式宣传为与离线文件等价。
- 浏览器内的“创建房间”同样依赖网站代码。对网站不放心时，用命令行 `scripts/build-html-room.mjs room` 在自己的电脑上生成。

### 4.3 CSP 的作用与边界

文件内嵌的 CSP：`default-src 'none'`，脚本与样式只允许固定哈希，`connect-src` 只列出本房间配置的中继 origin，禁止图片、字体、框架、Worker、表单提交、`<base>`。自动化测试在真实 Chromium 中确认：注入的内联脚本、`eval`、对其他主机的 `fetch`、WebSocket、图片、`sendBeacon` 全部被拦截，一个本地计数服务器收到 0 次请求（同样的请求在没有 CSP 的对照页面中能到达）。

边界：

- `frame-ancestors`、`sandbox`、`report-uri` 在 `<meta>` CSP 中无效，文件模式也无法用响应头补上。
- CSP 只约束页面；不约束浏览器扩展、被入侵的操作系统、输入法、截屏。
- CSP 不替代代码审计。客户端代码不使用 `eval`、`new Function`、`innerHTML` 一类接口，单元测试会扫描这一点。

## 5. 中继与 `Origin: null`

本地文件发起的 WebSocket 握手带 `Origin: null`。原有 `/ws/` 只接受同源，以防别的网站借访客浏览器连接中继。`/hr/` 额外接受字面值 `null`，理由是：

- 进入房间靠 `access`（由 Master Secret 派生，中继以 `SHA-256(access) == Room ID` 常数时间校验），不知道 Master Secret 的页面——包括任何沙箱 iframe——拿不出它。
- `Origin` 从不被当作身份：浏览器之外的程序本来就可以发送任意 `Origin`。
- `/hr/` 房间在中继内使用独立命名空间（`hr:` 前缀），与原有房间互不相通，不参与公开大厅、裁判和图片；原有端点的 Origin 规则不变，并有回归测试。
- 速率限制与原有端点相同（每地址每分钟加入次数、每连接帧预算）。

## 6. 成员、在线状态与送达

- **成员身份**是中继分配的编号加上该成员本次访问的签名密钥。没有长期身份、没有昵称。两个编号可能是同一个人的两个标签页；编号不证明“独立的真实设备”。
- **安全码**（20 位）由在场所有人的签名公钥计算。通过电话或当面核对一致，才能说明没有人被中继调包。
- **在线成员**来自中继的成员列表，是尽力而为的信息：断线的人在 2 分钟内可以用原编号回来；刷新页面是一个新成员。
- **送达状态**：排队中 → 发送中 → 已提交中继（中继把消息回传给发送者）→ 部分 / 全部目标成员已确认；或发送失败。“目标成员”是加密这条消息时在场的其他成员快照，之后加入的人不计入。确认（`seen` 帧）只在接收方验签解密成功并显示消息后发出，由房间密钥封装，AAD 绑定房间、发送者编号和帧类型；它能证明“房间里持有密钥的那个编号确认了”，不能证明对方是谁——这一点要靠核对安全码。

## 7. 本地数据

V1 不使用 Cookie、`localStorage`、`sessionStorage`、IndexedDB。消息、成员编号、设备密钥只在页面内存中，关闭或刷新即消失；离开房间时丢弃引用（网页无法强制浏览器覆写内存）。存储适配器存在，但默认只用内存后端。

## 8. 环境不满足时

启动时实际调用一遍所需算法（HKDF、AES-GCM、ECDH/ECDSA P-256、HMAC，加锁文件还有 PBKDF2），并检查 WebSocket、BigInt（ML-KEM 需要）。任何一项不可用都显示中文说明，**不会**退回到不安全的实现。脚本根本无法运行时（例如某些应用内预览只渲染 HTML），页面上的静态说明文字仍然可见，不会白屏。
